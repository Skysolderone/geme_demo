## Context

这一层容易被当作"美术和界面"而推迟，但它承担两件不可推迟的事：

1. **信息边界是规则的一部分**。§13 规定哪些信息始终公开、哪些必须隐藏，这同时定义了正式 AI 的读取边界（§15.1）。它必须在数据层成立，而不是靠界面遮挡——否则任何一次"临时调试加个字段"都会静默破坏公平性。
2. **批次预演决定玩法能不能被理解**。§14.1 列的六项预演信息不是便利功能：没有"预计提子"，玩家无法规划围杀；没有"军势预览"，构筑爆发变成盲盒；没有"自杀风险"，合法性规则变成随机报错。

本 change 定义**必须呈现什么、必须隐藏什么、交互的语义是什么**，不指定 UI 框架、渲染技术或控件形态。

## Goals / Non-Goals

**Goals:**
- 信息边界在数据层落实，公开视图与私有视图结构分离。
- 批次预演的六项信息完整、准确、零副作用。
- 非法批次原因可定位、文案不含糊。
- 五种信息层各自的职责清晰，不互相越权。
- 视觉基准可被检验（去色可辨、缩略图可辨、装饰不遮挡判读）。

**Non-Goals:**
- 不指定 UI 框架、渲染技术、分辨率或控件实现。
- 不实现正式美术资源、动画、镜头与音效。
- 不实现联网观战视角与延迟处理。
- 不实现 AI 决策的可视化调试。

## Decisions

**D1：公开视图与私有视图是两个结构，不是一个结构加权限标志。**
与 `add-heuristic-ai` 的 D1 是同一条决策的两面。公开视图里根本不存在"对手手牌数量"这个字段；需要它的地方只有该玩家自己的私有视图。这样 §13.2 的四条隐藏规则成为结构性保证。
副作用：UI 需要按"我是谁"选择视图来源。这个成本远低于"到处检查权限"。

**D2：预演信息全部来自 `add-batch-deployment` 的预演结果，UI 不自行计算。**
UI 绝不能自己算一遍"哪些棋串会被提走"——两处实现必然漂移，且漂移的表现是"预览说会提子，确认后没提"，这是最伤玩家信任的 bug。预演结果必须一次性带回 UI 需要的全部六项内容。
这反过来对 `add-batch-deployment` 提出要求：预演结果的载荷要足够丰富（提子集合、己方棋串气、各棋串军势预览、势力与排名变化）。

**D3："将揭示"是预演结果里的一个标志位，不是 UI 的推断。**
UI 若自行判断"这个格子将被覆盖所以会揭示"，就需要知道覆盖规则——职责泄漏。由预演结果直接给出"该格将首次进入覆盖范围且当前未揭示"的标志。

**D4：信息层是纯读视图，与游戏状态严格单向。**
信息层不持有任何可变状态，不发出任何改变对局的调用。加测试：开关信息层任意次数后对局状态序列化不变。

**D5：按住/点击切换做成同一套状态机的两种输入映射。**
"按住显示"与"点击切换"共享同一个"信息层是否可见"状态，只是进入/退出的触发条件不同。这样辅助设置的切换不需要两套逻辑，也不会出现两种模式行为不一致。

**D6：视觉基准的每一条都要有可检验的判据。**
"亲和但不幼稚"无法验收；"去色条件下仍可通过旗帜图形与棋子轮廓区分阵营"可以。本 change 把 §20 的风格描述逐条转成可检验的断言：去色可辨、小尺寸缩略图可辨、装饰不遮挡合法落点/气/归属的判读、UI 无手游式大按钮与夸张弹窗。
主观的气质部分保留为设计指引，不写成 spec 要求。

**D7：顺序层必须能解释"为什么是这个顺序"。**
§11.2 的先手值公式与三级同值判定链对玩家是不透明的。顺序层要列出名次、修正、先手值与预测顺序——玩家随时能查清下一轮为什么这样排，否则先手正反馈会被体验为"系统偏袒"。

## 接口契约

**输入：**

| 输入 | 来源 |
|---|---|
| `公开视图`（盘面、已揭示信物、势力明细、行动顺序、手牌类型） | 各规则 change 的公开输出 |
| `当前玩家私有视图`（手牌数量、两段账、征募面板、暂放状态） | `add-recruit-hand`、`add-batch-deployment` |
| `预演结果`（六项预演信息 + 失败类别与坐标 + 将揭示标志） | `add-batch-deployment` |
| `空格归属表`、`势力明细` | `add-territory-power` |
| `信物公开状态` | `add-relic-system` |
| `阶段状态`、`行动顺序 + 先手值明细`、`玩家状态` | `add-match-flow` |
| `人工接管入口` | `add-heuristic-ai` |

**输出：** 本 change 只消费，不向规则层输出任何改变状态的调用；唯一的输出是玩家的操作意图（暂放/撤销/确认/Pass/弃赛/选取候选/整类弃牌），全部经由既有规则接口执行。

## Risks / Trade-offs

- **[UI 自行计算预演导致与规则漂移]** → 硬约束：UI 不得包含任何规则计算。加检查：UI 层不依赖棋串/气/军势的计算模块，只依赖预演结果结构。
- **[隐藏信息经由界面泄漏]** → 结构分离（D1）+ 测试断言公开视图不含四类隐藏字段。
- **[信息层过多导致玩家认知负担]** → 五层各自职责单一，且默认棋盘保持干净；按住才显示是刻意的设计，避免常驻信息墙。
- **[预演载荷过大影响响应]** → 预演在每次暂放变更时都会触发。缓解：预演结果可分级（轻量结果用于即时反馈，完整军势/排名预览按需计算），但合法性判定必须始终完整。
- **[视觉风格描述无法验收]** → D6 把可检验的部分写成 spec，主观部分留作指引。
- **[顺序层暴露过多信息]** → 顺序层的全部内容都属于 §13.1 的"始终公开"范畴，无泄漏风险。

## 裁决记录（已确认）

1. **批次预演显示完整排名变化**，包含其他玩家被挤动的名次。势力与排名均属 §13.1 的始终公开信息，无泄漏风险；"这一手能把谁挤下去"恰好是评估先手收益的关键信息。
2. **危险棋串阈值：气 ≤ 2 标记为危险、气 = 1 标记为紧急**，阈值可配置，跑局后按玩家反馈校准。批次落子下对手一次能下好几枚，2 口气已经是真危险，只标 1 口气往往来不及反应。
3. **信息层一次只显示一层**。每一层都要压低场景饱和度来突出自己，叠加后两层会互抢视觉优先级，且任意叠加意味着要为 31 种组合设计优先级。若玩家反馈强烈需要"领地 + 气"同看，再单独评估。
4. **Pass 确认前必须明确警示"确认 0 落子将撤销本轮新征募的 N 枚棋子"**，但不要求二次确认。§5.5 的撤销规则对新玩家完全不直觉，不提示会被体验成"牌莫名其妙没了"；而 Pass 是合法且常见的战术选择，二次确认会在死局阶段拖慢节奏。
6. **表现形式：3D 低多边形，固定倾斜俯视镜头**（2026-09-15，项目负责人指向参考图后确认）。参考图从 `Siege-玩法介绍-v1.docx` 解出，存于 `art/style-exploration/`：`siege-style-03-low-poly-fantasy.png`（视觉基准）与 `fig1`–`fig8`（开局、手牌面板、批次预演、提子前后、领地层、信物揭示、棋子轮廓、倍增军势）。棋盘与棋子用程序生成的低多边形几何体实现参考图轮廓——普通子=圆头兵、堡垒子=塔楼、连珠子=双球连杆、倍增子=金字塔、协同子=多瓣水晶；四方主色红/蓝/金/紫，旗帜图案三角/塔楼/太阳/莲花。HUD 布局按参考图：左上回合旗标、顶部中央行动顺序条、右上排名、左下手牌、底部中央五个信息层按钮（Territory / Liberties / Influence / Relic / Hand，对应领地/气/势力/信物层与手牌面板；顺序层并入顶部顺序条的展开视图）、右下结束回合。树木、遗迹、水面、悬崖等装饰与正式美术资源不在本 change 范围；障碍格用简单岩石几何体表示。
7. **视觉规格的验收方式**：可自动化的部分只断言数据层——四方旗帜图案两两不同、五种棋子轮廓标识两两不同、合法落点/气/归属的高亮层独立于装饰层；"去色可辨 / 缩略图可辨 / 装饰不遮挡"由项目负责人按截图检查清单人工确认，第一版不做图像比对。
8. **新建 `src/Siege.Presentation`（net8.0，零 Godot 依赖）**：承载预演六项载荷的呈现模型、信息层状态机与各层内容、手牌面板内容、可见性规则。本 change 的 Scenario 测试绝大部分落在这里，用 xUnit 在 `tests/Siege.Core.Tests/` 下测，不需要启动 Godot。
9. **预演载荷在 `Siege.Core` 组装**：现有 `RehearsalResult` 只有合法性、失败、提子与预演盘面；六项信息里的己方棋串气、军势预览、势力与排名变化、"将揭示"标志由 Core 侧复用唯一实现（`PowerCalculator`、`CoverageMap`、棋盘气查询、信物公开状态）组装为富预演结果。Presentation 与 Godot 都不做规则计算。
10. **Godot 工程在 `src/godot/`，使用独立解决方案，不加入 `siege.sln`**：`dotnet test` 不依赖 Godot SDK。工程 `Godot.NET.Sdk` 版本 4.7.2，目标 net8.0，引用 `Siege.Core` 与 `Siege.Presentation`。
11. **对局驱动**：人类玩家的回合由界面直接调用 `MatchFlow` 的阶段接口（整理 → 征募 → 部署 → 确认/Pass）；AI 回合在主线程逐个小回合执行，回合间留出可见停顿并展示落子与提子。沿用 match-flow 裁决"单线程 + 快照发布"。
12. **输入**：键鼠与手柄用 Godot InputMap 的两组独立动作配置；"按住显示 / 点击切换"是 Presentation 层同一可见性状态机的两种输入映射（D5）。
13. **派发**：顺序两段。阶段 A = Core 富预演 + `Siege.Presentation` + 全部可无头测试的 Scenario；阶段 A 完成后本地 wip 提交。阶段 B = `src/godot/` 渲染、输入、HUD 与视觉，主会话用 Godot 命令行无头构建 / 启动核实后交项目负责人试玩。
5. **未发现的信物格在默认棋盘上统一显示为"未知信物"标记**，不在格子上区分强度预算分区；分区信息属地图公开信息，可在信物层查看。保住"未知格把路线变成选择题"的开局张力，而不是把探索压缩成"直接冲高档区"。
