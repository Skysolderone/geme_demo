## Context

`BoardView.Build` 逐格创建节点：地砖、场景面砖（`AddSceneSlab`）、障碍装饰（`TerrainParts.Create(Rock|Pines|Ruins, variant)`，造型按坐标散列挑选）。`TerrainParts` 的部件有"资源加载"与"程序生成"两种来源。棋子层 `DrawPieces` 在 `Refresh` 与演出期间的 `RefreshShow` 里整层清空重建。性能读数由既有 `[perf]` 日志行给出（帧率、单帧处理、绘制调用、对象数）。

## Goals / Non-Goals

**Goals**：棋盘图绘制调用数降一个数量级；演出期间不整层重建棋子；画面逐像素不变。**Non-Goals**：见 proposal。

## Decisions

### D1 先测量、定基线

窗口模式（非 headless，headless 没有真实渲染读数）下取四组读数：`board:1` 静止帧、`board:1` 演出进行中、`board:1:n10` 静止帧、v5 静止帧。每组取 `[perf]` 行的帧率、单帧处理、绘制调用、对象数。定帧截图各一张作画面基线。

### D2 场景装饰与面砖用 MultiMesh

同一网格 + 同一材质的装饰归入一个 `MultiMeshInstance3D`，每格一个实例变换（位置 / 朝向 / 缩放与现状逐格相同）。装饰若由多个子网格组成（如松树丛的几棵树），按子网格分别建 MultiMesh，实例变换 = 格变换 × 子网格局部变换。变体挑选规则（按坐标散列）不变。

场景面砖同理：一种材质一个 MultiMesh。

**2026-10-03 实测修正**：第一轮只合批场景装饰与面砖，绘制调用只降到 0.70（`board:1` 4097 → 2873），原因是装饰本来就共享网格与材质、渲染器已自动合并；剩余调用的 72%–76% 来自可落子地砖（面砖 + 衬底 + 侧面色带，每块独立网格 + 独立材质，`board:1` 上 1058 个节点）。原稿"可落子格数量少"在棋盘图上不成立。第二轮：地砖节点保留（拾取走层数表，不依赖网格节点），同基色、同尺寸的地砖共用同一份网格与材质，由渲染器自动合并或改为 MultiMesh；压暗处理按基色整批换材质参数，结果须逐像素相同。

障碍格没有拾取需求（`PickCell` 对不可落子格返回空），合批不影响拾取。

### D3 演出期间增量重画棋子

`RefreshShow(mask)` 改为：维护"坐标 → 棋子节点"表；本帧遮罩与上一帧相比只处理变化的格（新出现、进度变化的出现动画、淡出进度变化、淡出结束移除）。演出结束后的那次完整 `Refresh` 保持整层重建，保证终态与非演出路径完全一致。

### D4 画面不变的证据

改前改后同参数定帧截图逐像素差分：差异 bbox 只允许落在已知的水面动画区域（v5：约 (574,283)–(1000,646)）；棋盘图无水面，要求 0 像素差异。演出进行中的截图用既有 `--shot-show=` 自证行逐字相同 + 像素差分。

### D5 验收数字

`board:1` 静止帧绘制调用数降到改前的 1/5 以下；演出进行中单帧处理耗时不高于静止帧的 1.5 倍。帧率与机器有关，只报告。

## Risks / Trade-offs

- MultiMesh 的实例无法逐个做信息层压暗（`SceneTreatment` 的装饰对比度）→ 压暗改为改材质参数或整批调色，结果须与现状逐像素相同；做不到就对受影响的那一类装饰保留逐节点方式并在报告里说明。
- 程序生成的部件每件网格不同（带 variant）→ 先按 variant 归并统计，若变体数有限则每个变体一个 MultiMesh；若每格都不同则无法合批，改为合并网格（一次性烘成一张大网格）。

## Migration Plan

纯实现替换；回滚 = 还原 `BoardView` / `TerrainParts`。
