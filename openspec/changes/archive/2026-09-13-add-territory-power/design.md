## Context

设计文档 §10 的公式看起来简单，落到实现上有四个必须一次做对的细节：

1. **取整位置**：`⌊(基础 + 加值) × 倍率⌋`，逐棋串各取一次。先求和再取整会系统性抬高分数。
2. **领地分绝不进倍率**：这是防止"倍增流"同时吃掉空间分的护栏，也是设计文档反复强调的一条。
3. **棋子所在格不重复计分**：棋子只通过基础军势计分，不再算一格领地。
4. **一切实时重算**：§9.2 与 §10.1 都明确要求，不保留成长层数。

另外，覆盖层同时服务两个消费者：空格归属（本 change）与信物控制（`add-relic-system`）。这两者必须共用同一份覆盖数据，否则会出现"领地层显示独占、信物却判争议"这类玩家无法理解的矛盾。

本轮规格保持实现无关。

## Goals / Non-Goals

**Goals:**
- 一份覆盖数据，同时支撑空格归属与唯一覆盖查询。
- 棋子效果计算可逐例验证，全部算例取自设计文档。
- 势力明细是稳定结构，UI 与遥测直接消费，不各自重算。
- 每次结算与 Pass 后的实时重算，结果只依赖当前盘面。

**Non-Goals:**
- 不做信物效果与控制归属。
- 不做先手值与行动顺序。
- 不做征募权重与徽记调权。
- 不做任何永久成长、击杀分、历史积分。

## Decisions

**D1：覆盖表按格存储"覆盖者集合"，而非按玩家存储"覆盖格集合"。**
判定独占/争议/中立需要的是"这一格有几个不同的覆盖者"，按格存储让三态判定与唯一覆盖查询都是 O(1) 读取。按玩家存储则每次判定都要做交集。
实现上只需存"覆盖者数量 + 若数量为 1 则存该玩家"，不需要完整集合——这同时天然满足"覆盖棋子数量不影响独占"。

**D2：全量重算，不做增量。**
与 `add-board-core` 的 D1 一致。一次提子可能同时改变覆盖、棋串分裂、连珠断线、倍率下降，增量维护的组合爆炸不可控。121 格 × 4 人的全量重算开销可忽略。

**D3：位置加值分来源计算并分别记账。**
连珠加值与协同加值各自独立算出后相加，明细中分开保存。理由：§17 要求分析"高倍率棋串的形成轮次、峰值及被摧毁概率"，以及各棋子的选择率与胜率；不分来源就无法归因是连珠流还是协同流。

**D4：连珠线的扫描方式——按最大极长线扫描。**
横向从左向右扫，遇到非己方连珠子即断；对每条极长的连续段，若长度 ≥2 则计 `L×(L−1)`。纵向同理。交叉点棋子自然会在横竖两次扫描中各被计一次，这正是 §9.2 要求的行为。必须有专门用例断言"不拆子区间"。
注意：连珠线的构成要求是**同一玩家的连珠子连续相邻**，与棋串归属是两个概念——一条连珠线必然在同一棋串内（四邻接相连且同玩家），但棋串可以包含多条互不相连的连珠线。

**D5：协同子的"其他类型数"只看同一棋串，且排除协同子自身类型。**
纯协同子棋串加值为 0。多枚协同子各自独立按同一个"其他类型数"计算，故总加值为 `协同子数量 × 其他类型数 × 2`。

**D6：倍率用精确有理数或定点数，不用二进制浮点。**
`1.5^n` 在二进制浮点下可以精确表示（1.5 = 3/2），但 `(基础+加值) × 1.5^n` 在 n 较大时会超出精确范围，而取整对边界值极其敏感——`16.499999` 与 `16.5` 取整结果不同。建议用"乘 3 除 2 的整数运算"或定点数实现：`结果 = (基础+加值) × 3^n / 2^n`，整数除法即向下取整。这样跨语言、跨平台结果完全一致，也便于跑局复现。

**D7：弃赛者棋子照常参与覆盖与势力计算。**
§12.2 明确要求。实现上意味着覆盖与势力计算不能过滤玩家状态；过滤只发生在"生成行动顺序"与"获胜判断"两处。这是一个很容易漏的边界，必须有用例覆盖。

## 接口契约

**输入：**

| 输入 | 来源 |
|---|---|
| 盘面（格占用、棋串、气） | `add-board-core` |
| 结算触发点（第 5 步） | `add-batch-deployment` |
| 玩家状态（参赛 / 已弃赛 / 已出局） | `add-match-flow` |

**输出：**

| 输出 | 消费者 |
|---|---|
| `空格归属表`（每格：独占者 / 争议 / 中立） | `add-tactical-ui`（领地层） |
| `唯一覆盖查询`（格 → 唯一覆盖者或无） | `add-relic-system`（信物控制） |
| `势力明细`（按玩家：领地分、独占格集合、逐棋串拆分） | `add-tactical-ui`（势力层）、遥测（§17） |
| `总势力` + `势力名次（含并列信息）` | `add-match-flow`（先手值、终局排名）、`add-heuristic-ai` |

## Risks / Trade-offs

- **[浮点取整偏差]** → 采用 D6 的整数/定点实现，并对 `1.5^n` 各阶做边界用例（恰好落在整数上的值必须取到该整数）。
- **[连珠拆子区间重复计分]** → 最容易写错的一处。用"长度 4 只计 12"的断言锁死。
- **[领地分误入倍率]** → 用"10 领地 + 倍率 2.25"的用例锁死。
- **[覆盖语义两处实现不一致]** → 强制 `唯一覆盖查询` 与空格归属读取同一份覆盖表，并加交叉一致性测试。
- **[全量重算在批量跑局下的开销]** → 与 board-core 同一取舍；先实测再优化，优化不得改变语义。
- **[高倍率棋串导致数值超出预期区间]** → §16 给出目标区间（中期几十到一百，成熟倍增串允许数百）。遥测需记录每局倍率峰值，由 `add-heuristic-ai` 的批量跑局回归。

## 裁决记录（已确认）

1. **连珠线按"同玩家 + 四邻接连续的连珠子"扫描**，不额外做棋串判定。四邻接连续的同玩家棋子必然同串，两种表述在结果上等价，不引入无意义分歧。连珠线 MUST NOT 穿越普通子、堡垒子等其他类型的己方棋子。
2. **协同子的"其他类型数"按字面排除协同子自身类型**。纯协同子棋串的位置加值为 0，逼玩家去做混合棋串——这正是该棋子的设计意图。
3. **倍率不设任何上限**，与 §8.1 的"不设统一数值硬上限"一致。护栏由遥测承接：记录每局倍率峰值与出现轮次；若破坏 §16 的数值区间，调整发生在 `add-recruit-hand` 的征募权重或 `add-relic-system` 的生成预算，**不在计分侧截断**。
4. **势力并列由流程层打破**：本层输出并列组信息，`add-match-flow` 用 §11.2 的三级同值判定链（先手修正 → 势力值 → 上一大回合行动更晚者）裁决。避免计分层反向依赖流程层的行动顺序数据。
