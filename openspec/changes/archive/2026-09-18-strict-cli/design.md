# 设计与裁决记录：strict-cli

## 1. 现状

`CommandLine` 的构造函数把所有 `--key [value]` 收进 `_options` 字典，`Get / GetInt / GetUInt64 / Flag / Has` 按名字取。没有任何一方检查"字典里还剩什么没人要"。

后果是一类静默失败：拼错的选项、改过名字的选项、从旧脚本抄来的选项，都表现为"命令正常执行，只是该配置项取了缺省值"。跑局命令尤其危险，因为它的产出是用来做平衡裁决的数据。实例：`--matches 200` 被完整忽略，`Count` 取缺省值 1，程序打印"跑局：1 局"并正常写出 `summary.json`。

## 2. 裁决

### D1：在 `CommandLine` 内记录消费情况，而不是各子命令维护白名单

白名单要人工同步，漏一个就是假阴性，加一个不存在的名字则是假阳性，两种错误都无人察觉。改为在每个读取方法里把 key 记进 `_consumed`，子命令解析完后调一次结算方法。读了什么就算认识什么，白名单不可能与实现脱节。

`Has(key)` 同样计入消费：条件读取（`if (cli.Has("screenshot"))`）里 `Has` 就是这个选项的读取方。

### D2：条件分支下未被读到的选项，报错是正确行为

若某选项只在另一选项存在时才被读取（例如只有给了 `--screenshot` 才读 `--shots-dir`），单独给出它会被判为未知选项。这是对的：用户给了一个在当前调用下不产生任何作用的参数，沉默地忽略它正是本 change 要消灭的行为。

### D3：报错要给出最相近的合法选项，但不建立别名

`--matches` 报错时提示 `--count`。不为它加别名——别名会把一次打错固化成接口的一部分，之后两个名字都得维护。

相近度用编辑距离，取距离最小且不超过 3 的候选；没有足够接近的就只报未知选项名与该子命令的全部合法选项。

### D4：报错时不得写出任何输出

结算必须发生在创建输出目录与执行对局之前。半份输出目录比没有输出更糟：它看起来像一次跑了一半的正常运行。

### D5：位置参数不在本次范围

位置参数的误用（多给、少给、顺序错）是另一类问题，且当前各子命令对它的处理方式不一致。本次只管选项。

## 3. 不做的事

- 不引第三方解析库。当前实现总共 66 行，加一个消费集合即可。
- 不改任何现有选项的名字。
- 不为历史错名加别名。
