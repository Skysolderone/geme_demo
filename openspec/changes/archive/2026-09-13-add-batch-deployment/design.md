## Context

设计文档 §6.1 把合法性判定写成一个六步流水线，其中第 3–5 步（模拟整批 → 同时提子 → 再查自杀）是整个游戏最容易实现错的地方。传统围棋引擎按"一手"建模，自杀与打劫都在单手语境下判定；这里必须把"一手"换成"一批"，且提子是**同时**发生的集合操作，不是按顺序逐条移除。

同时，本 change 是整局状态机的心脏：正式结算顺序（§6.3）决定了信物揭示、势力重算、排名与终局检查的先后。这个顺序一旦被下游各自"就近"实现，就会出现"提子前算的领地"这类难以复现的 bug。

本轮规格保持实现无关。

## Goals / Non-Goals

**Goals:**
- 整批最终状态判定合法性，且预演对正式盘面零副作用。
- 同时提子的结果与移除顺序无关（顺序无关性可测）。
- 盘面同形禁则严格基于"合法批次结算后盘面"，中间态不入集合。
- 正式结算顺序在一处实现，下游只作为被驱动的步骤。
- 非法原因可定位到具体坐标/棋串/历史序号，直接服务 UI 高亮。

**Non-Goals:**
- 不产出部署上限、合法落子范围、手牌库存这三个输入的数值来源。
- 不实现信物揭示、势力重算、排名与终局的具体计算。
- 不实现击杀触发型棋子效果。
- 不实现批次的 UI 交互与可视化。

## Decisions

**D1：预演在盘面副本上执行，正式结算重新走一遍完整顺序。**
预演产出"是否合法 + 失败原因 + 预计提子集合 + 预计结算后盘面"，但 MUST NOT 把副本直接提升为正式盘面。理由：正式结算还要按 §6.3 驱动手牌扣减、信物揭示、势力重算、排名与终局检查，这些在预演中不应发生任何副作用；直接提升副本会让"预演是否含副作用"变成一个模糊地带。
代价：合法批次的盘面变换算了两遍。在 121 格规模下可忽略。
备选：预演即结算、失败时回滚——回滚路径要覆盖手牌、信物、势力、排名多个子系统，出错面远大于重算一次。

**D2：提子是集合操作，不是顺序循环。**
第 4 步必须先在"整批已放置"的盘面上**一次性算出**所有无气敌串的并集，再统一移除。若写成"遍历敌串，无气就移除，然后继续遍历"，两条互相提供气的敌串会因遍历顺序不同而得到不同结果。这一点必须有专门的顺序无关性测试（用随机遍历顺序跑同一批次，断言结果一致）。

**D3：自杀手检查只看"当前玩家的所有相关棋串"，范围取整批落点所在棋串的并集。**
落子可能把多条己方棋串合并成一条，也可能让远处己方棋串因敌串被提而改变气。保守做法：第 5 步重算当前玩家全部棋串的气。理由：全量重算与 `add-board-core` 的 D1（不做增量维护）一致，且 11×11 规模下开销可忽略，换来的是"绝不漏判"。

**D4：已提交盘面集合按"内容哈希 + 序号"存储，并保留完整序列。**
只存哈希集合能判重但无法告诉玩家"和第几次提交重复"，而 §14.1 要求非法批次必须说明具体原因。保留序号是低成本的可解释性投资。哈希碰撞需按内容再比对一次，不能只信哈希。

**D5：禁止预占"预计会被提空的格"是硬规则，不是 UI 便利。**
§5.4 明确写了这一条。它的作用是避免"先手玩家用一批棋子既提子又立刻占领腾出的关键点"，让提子后的空间成为下一手的公共争夺对象。实现上放在预演第 1 步（落点必须当前为空），先于模拟。

**D6：Pass 只发事件，不自己撤销征募。**
§5.5 的撤销规则涉及"本轮新增 vs 进入回合前已有"的区分，属于手牌与征募的账目，归 `add-recruit-hand`。本层只负责判定"确认 0 落子 = Pass"并发出事件，保持结算入口单一。

## 接口契约

**输入（由上游提供，本 change 不生产）：**

| 输入 | 来源 | 语义 |
|---|---|---|
| 部署上限 | 效果快照（`add-relic-system` / `add-match-flow`） | 一个正整数，无全局硬上限 |
| 当前合法落子范围 | `add-match-flow` | 允许落子的格集合；保护期内为锁定出生区，之后为全图 |
| 手牌库存 | `add-recruit-hand` | 按棋子类型的数量映射 |
| 盘面查询 | `add-board-core` | 取格子 / 取棋串 / 取气 / 序列化盘面 |

**输出（本 change 生产，下游消费）：**

| 输出 | 触发时机 | 消费者 |
|---|---|---|
| `预演结果` | 每次暂放变更或确认前 | `add-tactical-ui`（预演面板）、`add-heuristic-ai`（候选评估） |
| `手牌扣减请求` | 结算第 1 步 | `add-recruit-hand` |
| `盘面已变更` | 结算第 3 步之后 | `add-relic-system`（第 4 步）、`add-territory-power`（第 5 步） |
| `结算完成` | 结算第 5 步之后 | `add-match-flow`（第 6 步：排名、出局、终局） |
| `Pass 事件` | 确认 0 落子 | `add-recruit-hand`（撤销本轮征募）、`add-match-flow`（整轮 Pass 终局检查） |
| `提子记录` | 结算第 3 步 | `add-heuristic-ai` / 遥测（提子规模统计） |

## Risks / Trade-offs

- **[同时提子写成顺序循环]** → 这是最高危的实现陷阱。以随机遍历顺序重复执行同一批次并断言结果一致，作为强制回归。
- **[预演泄漏副作用]** → 每次预演后断言正式盘面序列化逐字节不变，纳入回归。
- **[高部署上限下预演次数爆炸]** → 部署上限无硬顶（§8.1），AI 枚举候选批次时预演调用量可能失控。缓解：预演接口设计为可批量、可提前中断；AI 侧的剪枝策略归 `add-heuristic-ai`（§15.2 已要求先筛落点再组合）。
- **[已提交盘面集合随对局增长]** → 一局 7–10 大回合、4 人，提交次数在数十量级，内存与比对开销可忽略；但必须随存档持久化，否则读档后同形失效。
- **[禁止预占腾空格可能让玩家觉得反直觉]** → 属设计意图，非缺陷。UI 必须把拒绝原因说成"该格当前已被占据"，而不是含糊的"非法落点"。

## 裁决记录（已确认）

1. **确认时必须重跑一次完整预演**，不信任任何缓存的预演结果。单机热座下盘面不会在预演与确认之间变化，但这条规则在未来联网时同样成立，现在固化的成本最低。
2. **自杀手检查采用全量重算**：第 5 步重算当前玩家的全部棋串，不收窄到"受影响子集"。提子可能让远处棋串也改变气，"受影响"的边界极易漏判，而漏判的表现是非法手被放行。与 `add-board-core` 的"不做增量维护"取舍一致。
3. **现在就在提子记录中保存批次内落子顺序**。本轮不实现击杀触发型棋子，但预留顺序字段的成本几乎为零；将来补"最后一手归功"时无需改动批次结构、提子记录与已归档的对局日志格式。
4. **盘面同形禁则全局生效，不区分提交者**。与 §6.2 字面一致，实现最简。4 人局的循环可能跨玩家形成，按玩家分别维护历史拦不住。跑局中监控"被他人历史盘面误伤"的发生频次，若成为高频问题再调整。
