## Context

征募与手牌这一层看起来是"抽卡 + 背包"，但它有两条不能含糊的账目：

1. **本轮新增 vs 进入回合前已有**。§5.5 要求 Pass 只撤销本轮新增；若手牌只存"类型 → 总数"，同类型的新旧棋子就无法区分，规则直接失效。
2. **类型槽是种类维度的约束，不是容量维度**。§5.2 强调同类型无限叠加。把它实现成"背包容量"会让整个构筑体验走样。

此外，本层是对局的第二个随机源（第一个是信物生成）。两个随机源必须各自独立推进、都由对局种子驱动，否则"用同一种子重放同一决策序列"无法复现——而 §17 的全部平衡分析都建立在可复现之上。

本轮规格保持实现无关。

## Goals / Non-Goals

**Goals:**
- 手牌账目能精确区分"本轮新增"与"回合前已有"。
- 类型槽严格是种类维度约束。
- 徽记调权公式与归一化可逐例验证。
- 征募随机可复现，且候选/选择/撤销全部可记录。
- 信息边界（候选私有、数量私有、类型公开）在数据层就成立，而不是靠 UI 遮挡。

**Non-Goals:**
- 不做棋子在盘面上的效果与计分。
- 不做部署与批次合法性。
- 不做信物效果的产生。
- 不做金币、付费刷新、棋子升级、数量羁绊。
- 不做手牌面板的可视化。

## Decisions

**D1：手牌存"类型 → (回合前基数, 本轮新增数)"两段账。**
小回合开始时把上一回合的总数折叠进"回合前基数"，本轮征募所得只累加到"本轮新增"。Pass 时把"本轮新增"清零；确认落子（≥1 枚）时把"本轮新增"折叠进基数。部署扣减优先从哪一段扣？
**裁决：先扣"本轮新增"**。理由：若先扣基数，一个玩家可以"征募 2 枚普通子 → 部署 2 枚基数中的普通子 → Pass"，从而既落子又保留……但注意落子后就不是 Pass 了，所以这个漏洞不存在。真正的差别只出现在"部署了但仍 Pass"这种不可能的状态上。既然两种扣法在合法流程中等价，选先扣新增，因为它让"Pass 撤销"变成简单的清零操作，减少出错面。

**D2：类型槽不单独存储，由手牌类型数派生。**
已占用槽位 = 当前数量 > 0 的类型数。这样"清零自动释放槽位"不需要任何额外维护，也不可能出现"槽位泄漏"。槽位上限来自效果快照。

**D3：归一化在抽取时进行，不预先存储归一化后的概率。**
徽记数量每小回合都可能变化（信物易主），预存归一化概率等于引入一份需要同步的缓存。每次生成面板时按当前快照的徽记数量现算权重并归一化，成本可忽略。

**D4：每个候选位独立抽取，用同一个种子序列连续推进。**
§9.1 明确"每个候选位独立抽取，允许重复类型"。实现上就是对每个候选位做一次加权抽样，序列连续推进。不做"不放回抽样"，不做去重。

**D5：征募随机与信物生成随机使用两条独立的子序列。**
从对局种子派生出若干命名子流（如 `relic-gen`、`recruit`），各自独立推进。理由：若共用一条序列，玩家决策导致的征募次数差异会改变后续所有随机取值，使"改一个决策就整局重放失效"，调试与回归都会变得极难。这是跑局验证的基础设施要求，必须在本 change 落地。

**D6：信息边界在数据层落实。**
征募候选存放在"当前行动玩家私有"的结构中，其他玩家与对战 AI 的读取路径根本拿不到；手牌对外只暴露"类型集合"视图，数量字段不在公开视图里。§15.1 要求正式 AI 只读公开信息，靠 UI 遮挡是守不住的。调试 AI 的全量读取（§15.3）走一条显式标记为测试专用的旁路。

**D7：强制弃牌是阻断式的，不是提示式的。**
§5.2 写的是"必须在征募前整类弃牌"。实现为小回合流程的一个前置门：超限状态未解除，征募阶段不开始。这样不需要在征募逻辑里到处检查槽位。

## 接口契约

**输入：**

| 输入 | 来源 |
|---|---|
| 效果快照（展示数、免费选取数、类型槽、徽记权重调整、超限种数） | `add-relic-system` |
| 手牌扣减请求（结算第 1 步） | `add-batch-deployment` |
| Pass 事件 | `add-batch-deployment` |
| 小回合开始 / 结束事件 | `add-match-flow` |
| 对局种子的 `recruit` 子流 | 对局初始化 |

**输出：**

| 输出 | 消费者 |
|---|---|
| `手牌库存`（私有视图：类型 → 数量） | `add-batch-deployment`（库存约束）、当前玩家 UI |
| `手牌公开视图`（类型集合） | `add-tactical-ui`（对手区域）、`add-heuristic-ai`（公开信息） |
| `手牌是否为空` | `add-match-flow`（出局条件） |
| `征募面板`（私有） | 当前玩家 UI、`add-heuristic-ai`（仅自己的） |
| `征募记录`（候选、选择、Pass 撤销数） | 遥测（§17） |

## Risks / Trade-offs

- **[两段账被实现成单一总数]** → 最高危陷阱。用"回合前 4 枚普通子 + 本轮新增 2 枚 → Pass → 剩 4 枚"这条用例锁死。
- **[类型槽被实现成容量]** → 用"14 枚普通子只占 1 槽"锁死。
- **[随机流共用导致重放失效]** → 子流隔离必须有测试：改变某玩家的一次征募选择，断言信物生成结果不变。
- **[归一化的浮点误差]** → 加权抽样建议用整数累积权重 + 整数取模，避免浮点归一化；调权公式 `×(1+0.75×n)` 可等价写成 `×(4+3n)/4` 的整数运算。
- **[信息边界被 UI 层绕过]** → 数据层就分私有/公开两个视图；加测试断言公开视图不含数量字段。
- **[玩家用"至少落 1 子"规避 Pass 撤销并拖延]** → §17 已把这条列为重点监控项。本层需输出"每回合落子数为 1 且势力无变化"的可统计信号，交由遥测分析。

## 裁决记录（已确认）

1. **免费选取数是上限，不强制取满**。玩家可以为了保留类型槽而主动少拿，这本身就是一个有意义的决策。
2. **满槽时，面板中的新类型候选照常展示但标记为不可选**，并给出"无可用类型槽"的原因。隐藏会让玩家误以为流派徽记没有生效，也看不到"弃掉一类就能拿"的机会成本。
3. **主动整类弃牌只允许在整理手牌阶段进行**，征募与部署阶段不可弃牌。这样"弃牌腾槽 → 征募新类型"的顺序是确定的，也避免玩家看到候选后才回头弃牌，从而保住类型槽的决策压力。
4. **Pass MUST NOT 撤销本轮的主动整类弃牌**。弃牌是玩家的主动决策且已明确"不返还任何资源"；一并撤销会让 Pass 变成无代价的试探手段（先弃牌开槽、看完候选不满意再 Pass 白嫖）。
5. **开局发放的 5 枚普通子计入"回合前基数"**，即开局即视为已有手牌。第一小回合 Pass 不会撤销它们——否则玩家第一手 Pass 就直接空手，近乎惩罚性缺陷。
