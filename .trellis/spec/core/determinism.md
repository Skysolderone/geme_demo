# 确定性

对局必须能仅凭种子 + 决策序列完整重放。§17 的全部平衡分析都建立在这一点上。

## 随机子流隔离

从对局种子派生以下几条**互相独立**的确定性序列（旧补给的征召签子流 `carry-draft:<编号>` 随补给删除，relic-redesign W2）：

| 子流 | 消费者 |
|---|---|
| `recruit` | 每小回合的征募候选抽取 |
| `setup` | 插旗后的首回合顺序、以及其他流程初始化 |
| `flag-pick` | 链接模式的盲选插旗（board-link-mode B2）：每名玩家按编号升序各抽一次 `[0, 出生棋盘数)`，未由人指定或时限到时未选的玩家取自己那一次的结果，不看已插的旗（`PrototypeZoneAssignment.AssignBlind` 与正式插旗共用）。retire-legacy-maps 删除了只服务旧路径的 `zone-pick`（边疆档种子选区）与 `flag-risk`（冒险抽签）两条子流 |
| `relic-spawn:<落位大回合>` | 挂在棋子上的信物的地图刷新（relic-redesign D2，`GameSeed.RelicSpawn(int)`）：每批一条，名字带该批的落位大回合（第 4、6、8……），在落位前 1 个大回合预告时一次抽完本批的位置与类型（逐件：先 `NextInt(剩余候选数)` 不放回抽格，再按 85 / 15 加权抽普通 / 稀有、普通四种 `NextInt(4)` 等权）；落位时不再抽。`RelicSpawner` 是唯一消费者，`MatchFlow` 在大回合开始时调用（接线段 W1）；预告随存档持久化（它是按预告那一刻的盘面抽的，存档里没有那一刻的盘面可以复算） |
| `relic-drop:<玩家编号>` | 出局 / 弃赛者手里未挂出的非保险带入件立即掉到地图（relic-redesign R17，`GameSeed.RelicDrop(int)`）：每名玩家一条（一名玩家只会出局或弃赛一次），候选规则与 `relic-spawn` 相同，逐件（按本局编号升序 = 清单下标顺序，编号在掉落时从对局游标分配）`NextInt(剩余候选数)` 不放回抽格，不占刷新上限；候选不够时多出的件消失。`MatchFlow` 在势力归零出局、战场落败、弃赛三处状态改完后调用（接线段 W2） |
| `carry-ai` | AI 带入（relic-redesign R21 / D5，`GameSeed.CarryAi`，唯一消费者 `PieceRelics.RelicCarryAi`）：件数 = 本机玩家带入件数（人机对局）或 `--carry-in`（批量跑局，0–5）；件数为 0 时不派生。消费顺序：按玩家编号升序，每名 AI ① 逐件 `NextInt(4)` 从普通四种（战鼓 / 号令 / 望台 / 百变的固定次序）抽 `count` 件；② 再逐件不放回 `NextInt(剩余未保险件数)` 抽 min(2, count) 件勾保险。稀有（军旗）不进 AI 带入。AI 的挂出不消费任何随机（段 C1 起：复摆后对每（件 × 落点）Clone 比较己方势力增量、贪心挂在增量最大的落点、前几批挂完，并列按非保险件 → 清单下标 → 坐标字典序打破，唯一实现 `Ai.RelicAttachPlan`；W2 的临时规则「按落子顺序挂」已替换） |

`relic-spawn` / `relic-drop` 按批次 / 玩家各派生一条，所以刷新与掉落都是纯函数：输入盘面、出生区域、种子、大回合、人数与场上未拾取件数即可复算本批，不需要持久化子流的消费次数；任一批的消费次数不影响其他批，更不影响上表任何既有子流。

改变其中一条子流的**消费次数**，MUST NOT 影响其他子流的取值。

**地图随机源不在这张表里，也不是 `GameSeed` 的子流**（map-generator D2，retire-legacy-maps 后只剩链接档）。链接图 `link:<地图种子>:<人数>` 的浮空岛布局用一条只由地图种子与人数决定的整数序列（`MapRandom.ForLinkLayout`，地表叠加另用 `ForLinkSurfaces`，与对局随机源同一份 PRNG 实现、独立的域常量；人数进入两条流的派生，同种子不同人数是不同的图；消费顺序写在 `LinkMapGenerator.Layout` 的 summary 里，生成器改消费顺序即换图，须重钉快照与基线）（对局中的拼接已随 open-map 删除）；两边互不可见：`MapRandom.cs` / `LinkMapGenerator.cs` / `LinkMapId.cs` 里不得出现 `GameSeed`，`Siege.Core/Match` 下不得出现 `MapRandom` 或地图种子——对局流程只拿到生成好的 `MapData` 与标识字符串。Core 永不读时钟：裸 `link` 的地图种子只在三个入口最外层取（经 `LinkMapId.FriendlySeed` 折成九位以内），取完即拼成完整标识，裸 `link` 不得写进任何记录。生成路径上同样禁浮点、禁时钟与环境（源码扫描守门 `链接档地图标识与确定性Tests.对局种子不影响地图` / `地图随机源与对局随机互不可见`）。旧 `gen:` / `board:` 生成器的尝试序号随机源（`ForAttempt` / `ForSurfaces` / `ForBoardAttempt`）已随生成器删除。

**为什么。** 若共用一条序列，玩家改一个征募决策就会让后续所有随机取值偏移，"改一个决策重放整局"立刻失效，调试与回归都会变得极难。

回归测试：改变某玩家的一次征募决策后，断言同一盘面上的信物刷新逐格不变（relic-redesign W1 前为"开局信物生成"，`relic-gen` 子流随旧信物删除）；另有"同种子同决策两局逐批相同"（`信物刷新接入对局Tests`）。

## 禁止浮点参与计分

倍率 `1.5^n` 与棋串军势 MUST 用整数运算（restore-go-core-rules 之后：倍率放大"基础军势 + 全部位置加值"，不封顶）：

```
棋串军势 = (基础军势总和 + 位置加值) * 3^n / 2^n   // n = 倍增子数，不封顶；整数除法即向下取整
总势力   = 独占空格数 + Σ棋串军势                  // 领地分不进倍率
```

禁止 `double` / `float` 出现在任何计分、倍率、取整路径上。唯一例外是 `Siege.Presentation.Camera` 下的相机几何类型（frontier-map）：守门 `内核与表现层不出现浮点` 按**精确类型名单**豁免它们，不按命名空间放行——往该命名空间里新塞一个带浮点的类型仍会红。相机不进规则、不进日志。

**为什么。** 取整对边界值极其敏感——`16.499999` 与 `16.5` 的 `Math.Floor` 结果不同。整数运算让跨平台、跨架构结果完全一致，这是跑局复现的地基。

注意取整位置：**逐棋串各取一次**，不在求和阶段或对总势力二次取整。两条未取整军势各 16.5 → 分别取整为 16+16=32，不是先求和 33 再取整。

## 并列必须确定性打破

任何排序、选择、候选评价出现并列时，MUST 用确定性规则打破（如坐标字典序），MUST NOT 使用不受控随机。

需要行为多样性时，通过种子驱动的扰动引入，而不是通过 `Random.Shared`。

## 集合操作不得依赖遍历顺序

同时提子（设计文档 §6.1 第 4 步）必须先**一次性算出**全部无气敌串的并集，再统一移除。

写成"遍历敌串，无气就移除，然后继续遍历"，两条互相供气的敌串会因遍历顺序不同得到不同结果。

强制回归：以随机化的遍历顺序重复执行同一批次 100 次，断言提子集合与结算后盘面完全一致。

## 持久化文本必须容忍行尾差异

`BoardHistory.Deserialize` 曾对 `\r\n` 零容忍：`\r` 会混进盘面串，让同形比对**静默失效**——比抛异常更糟，因为对局照常进行、规则却悄悄失守。任何解析持久化文本的地方都要 `TrimEnd` 行尾，其余偏差仍抛 `FormatException`。守门测试要含一条 CRLF 往返。

## 全量重算与受影响子集等价的论证（自杀手检查）

每次合法结算后全盘棋串都 ≥1 气（第 4 步移除无气敌串、第 5 步保证己方有气）。下一批次中只有落点会减气，减的是**邻接格**的气；己方棋串若因此失去最后一口气，那口气所在格上放的是己方子，与该串四邻接即合并为同一串——所以"无气的己方串"必然包含本批落点，全量重算 ≡ 只查受影响子集。全量的额外价值只在防御被绕过规则写入的脏盘面。结论：**按裁决 2 保持全量**，不做"收窄"优化，它没有收益。

## 势力 / 军势用 `BigInteger`，不用定宽整数

倍率 `3^n / 2^n`、棋串军势、总势力与名次比较 MUST 用任意精度整数 `System.Numerics.BigInteger`。

**这条在 restore-go-core-rules（2026-09-21，裁决 #1）翻过一次向。** 此前倍率指数封顶 3，`3^n` 恒小，规范写的是"用 `Int128` checked，不用 `BigInteger`"，理由是零分配、且装不进 `long` 时抛 `OverflowException` 算响亮失败。裁决 #1 取消封顶后该前提作废：`n` 的上界是地图可落子格数（边疆图 411），`3^81` 就已经越过 `Int128`，"溢出即响亮失败"会变成把合法局面判成崩溃。`BigInteger` 之外的任何定宽类型都 MUST NOT 出现在计分路径上；`checked` 的响亮失败路径随之取消——规格要求的是**精确、不溢出、不截断、不饱和**。

当年弃用 `BigInteger` 的分配开销仍然存在，但实测未构成问题：段 A 全量测试 45–55 s，与改动前的 55 s 基线持平。段 F 的 20 局冒烟（Standard、28 并行、单串军势最高 29776）AI 单步决策均值 421.62 ms、20 局墙钟 99.7 s，未见大数运算成为瓶颈；规则同时改变，没有可逐局对照的定宽整数基线，严格对比留给 `ai-eye` 的增量计算评估。

`System.Text.Json` 不支持 `BigInteger`，存档与跑局日志各注册一次 `Siege.Core.Scoring.BigIntegerJsonConverter`：写出为不带引号的精确十进制整数（小数值与旧的 `long` 写法逐字节相同），读入接受整数与整数字符串，小数 / 指数一律 `JsonException`，全程不经浮点。
