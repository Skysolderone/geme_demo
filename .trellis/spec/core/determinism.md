# 确定性

对局必须能仅凭种子 + 决策序列完整重放。§17 的全部平衡分析都建立在这一点上。

## 随机子流隔离

从对局种子派生三条**互相独立**的确定性序列：

| 子流 | 消费者 |
|---|---|
| `relic-gen` | 信物内容生成（开局一次性） |
| `recruit` | 每小回合的征募候选抽取 |
| `setup` | 插旗后的首回合顺序、以及其他流程初始化 |

改变其中一条子流的**消费次数**，MUST NOT 影响其他子流的取值。

**为什么。** 若共用一条序列，玩家改一个征募决策就会让后续所有随机取值偏移，"改一个决策重放整局"立刻失效，调试与回归都会变得极难。

回归测试：改变某玩家的一次征募决策后，断言该局信物生成结果逐格不变。

## 禁止浮点参与计分

倍率 `1.5^n` 与棋串军势 MUST 用整数运算：

```
棋串军势 = (基础军势总和 + 位置加值) * 3^n / 2^n     // 整数除法即向下取整
```

禁止 `double` / `float` 出现在任何计分、倍率、取整路径上。

**为什么。** 取整对边界值极其敏感——`16.499999` 与 `16.5` 的 `Math.Floor` 结果不同。整数运算让跨平台、跨架构结果完全一致，这是跑局复现的地基。

注意取整位置：**逐棋串各取一次**，不在求和阶段或对总势力二次取整。两条未取整军势各 16.5 → 分别取整为 16+16=32，不是先求和 33 再取整。

## 并列必须确定性打破

任何排序、选择、候选评价出现并列时，MUST 用确定性规则打破（如坐标字典序），MUST NOT 使用不受控随机。

需要行为多样性时，通过种子驱动的扰动引入，而不是通过 `Random.Shared`。

## 集合操作不得依赖遍历顺序

同时提子（设计文档 §6.1 第 4 步）必须先**一次性算出**全部无气敌串的并集，再统一移除。

写成"遍历敌串，无气就移除，然后继续遍历"，两条互相供气的敌串会因遍历顺序不同得到不同结果。

强制回归：以随机化的遍历顺序重复执行同一批次 100 次，断言提子集合与结算后盘面完全一致。
