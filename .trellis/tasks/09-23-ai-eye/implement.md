### 待决

1. **威胁的"敌方"口径**：目前只计参赛（Active）敌方，与敌损"参赛敌方势力下降"同一口径；弃赛 / 出局者遗留的非活形棋串不计入威胁。design D1 原文只写"敌方"，请负责人确认。
2. **"直三点中间"两条算例的解读**：tasks 1.2 写的是"未成活形时增量 1；成活形时 +3"。同一棋串在点中间后必然眼值 ≥ 2、成为活形，所以"未成活形"的情形按"本手没有新增活形"来实现，即棋串本就已活（另有单格眼），点直三中间只得眼值增量 1。若原意是别的盘面（例如两个单格眼分属两条棋串），需另补算例。
3. **与 life-shape R8（活形过易）的耦合**：开局第 1 个小回合，平台角上的 3 子就已是已确定活形，于是活形中性把安全维直接推到常数上限（种子 31：安全 12 → 36），20 局平均结束大回合 18.6 → 10.85。这正是 R3 要求段 D 开工前先裁决 R8 的原因；段 A–C 不受影响。
4. **性能**：非简单难度下，每次评价都会多做一次 `LifeShapeReport.Analyze`（每个盘面一次，三维共用）。段 C 做缓存与耗时对比，可以先拿这组粗略参照：种子 1–20（Standard、v5、28 路并行，非受控测量），每个小回合的平均耗时由改动前的 567639 ms / 1252 ≈ 453 ms 变为段 A 后的 324769 ms / 813 ≈ 399 ms。
5. `openspec list` 里新出现 `terrain-surfaces`（0/36），不是本任务所建，也未触碰；0.1 的"只剩本 change"只对开工时刻成立。

### R11 结论：硬约束**不**进预筛

硬约束有两个判据，分开看：

1. **"原活形失活"**：要对预演后的盘面做活形分析。放进预筛，等于把 3.1 刚去掉的活形查询加回来——本批边疆图 20 局的预筛共预演 393,573 格，己方有活形时每格都要多一次分析。这违反"确实更省"，也会让「预筛阶段不触发活形查询」变红。所以不做；这一条由构造可知，没有另外跑。
2. **"落点是己方单格眼"**：用批次前的缓存就能判，O(1)，可以在预演之前直接跳过。为此做了临时探针：`PrefilterCells` 跳过己方单格眼格，其余不变（探针已还原，逐字节一致并 `os.utime`）。在边疆图 Standard、种子 1–20、截断 80、完整事件流下与段 C 比对：
   - 省下多少：跳过 4,817 / 393,573 个预筛格，总预演次数 677,450 → 672,805，**只省 0.69%**。
   - 结果变没变：去掉每小回合的预演计数字段后，**17/20 局分叉**，只有 3 局相同。首个分叉都是真实的落点变化，例如种子 1 第 62 个小回合，`[G20 连珠, E27 倍增, H29 普通]` 变成 `[E27 倍增, H29 连珠]`。原因是被跳过的眼格让出了前 K 的一个名额，第 K+1 格进入完整枚举，改变了排行与组批。这违反"完整枚举阶段的结果不变"。
   - 两个条件都不满足，**不加**。

## 段 D1（tasks 4.1–4.3）——结构基线、逐维扫档、PowerGain 占比

### 开跑前定死的口径与选档规则（写于看数据之前）

- 每批：`siege-4p-base-v5`、种子 1–200、4 名 Standard AI、`TurnLimit = 600`、`SnapshotsOnly`、并行度 0（28）。权重与阈值只经配置文件给（`Players[].Difficulty` + `Weights` + `PassThreshold`），不传 `--difficulty` / `--players`（testing.md「扫档必须核对 config.json」）；`metrics.py` 逐局核对日志首部的地图、权重、阈值与批次 `config.json` 一致，不一致即断言失败。
- 每批三步：`run` → `analyze --dir`（report.txt）→ `metrics.py`。一致性断言：`summary.json` 的 `Truncated` 与逐局 `result.Truncated` 计数相等；report「整局无冲突 N 局」与逐局"无任何 `Captures`"计数相等。
- 指标口径：截断率 = `turn_limit` 局 / 200；结束大回合取全部 200 局的 `result.MajorRound`；整局无提子 = 全局没有任何小回合有 `Captures`；首次活形确立 / 首次提子大回合取有该事件的局的均值；第 3 大回合领先者胜率取 report 口径 A。
- 分解值占比：每个已确认批次（`Settled` 事件带 `Total`）的 `|w_i × raw_i| / Σ_j |w_j × raw_j|`，报中位数、均值、聚合（Σ|w_i raw_i| / Σ全部）三种口径；4.3 的"中位数占比"指 `PowerGain` 的逐批中位数，另报 `PowerGain` 占比 > 80% 的批次比例作辅证。
- 选档（design D6 第 3 条 + R20，词典序）：
  1. 截断率 ≤ 5%（不满足的档淘汰；全部不满足则取截断率最低档）；
  2. 整局无提子 ≤ 5%。若所有剩余档都达不到，取无提子最低档；与最低档相差 ≤ 2 局（1%，视为噪声）的档并列进入第 3 步；
  3. 平均结束大回合离 7–10 区间最近（落在区间内即距离 0）；再并列取离初值 / 上一维已选值最近的档；
  4. 第 3 大回合领先者胜率只记录，不作否决。
- 相邻两档之间无提子率跨过 5%、或截断率跨过 5% 时，在两档之间加密再下结论（testing.md「临界区要加密档」）。
- 与已跑批次权重 + 阈值完全相同的档直接引用已有目录，不重跑。
- 脚本：`sim-out/ai-eye-scripts/`（`mkcfg.py` 生成配置、`batch.sh` 三步串行、`metrics.py` 汇总与断言、`seqdiff.py` 逐种子比对落子序列）；每批配置 `cfg-<批名>.json` 与运行日志也在该目录。

- 截断局全部是**互提循环**：60 个截断局（全部批次合计）中 55 局末 40 个小回合的落点只在 ≤ 6 格内，且 ≥ 50% 的小回合有提子；其余 5 局落点 7–11 格、提子率 95%–100%。例：`ai-eye-eye-200` 种子 15，600 个小回合里 555 个有提子，末 12 个小回合四人轮流在 C4 / C5、M8 / M9 两处互提（`cycles.py`）。
  - 原因（已核实）：盘面同形的判重键是 `GameBoard.Serialize()`，每格写"归属 + 棋子类型码"，再附上累计的地形改造（`SettlementDriver` 记入 `BoardHistory`，`BatchRehearsal` 用同一串查重）。按日志逐手重建盘面（`korepeat.py`；重建结果与终局快照逐格一致；含改造时"归属 + 类型"键在全局零重复，与超级劫一致）：`ai-eye-eye-200` 的 8 个截断局与 `ai-eye-pass-80` 的 2 个截断局，末 100 次提交里**只看归属 + 改造、不看类型**的盘面，与窗口内更早的盘面重复 34–88 次。也就是说，同一个归属局面反复出现，只是每轮落下的棋子类型不同（连珠 / 要塞 / 倍增），判重键不同，所以超级劫放行。
  - 这是规则层的问题，调权重只能降低出现频率（PassThreshold 80 把截断从 8 局压到 2 局），消除不了。

### 4.3 PowerGain 占比

- 18 个参数点里，`PowerGain` 逐批中位占比最高 12.5%（Eye 0），选定组合 6.8%（均值 9.2%、聚合 7.3%），远低于 80%；占比 > 80% 的批次在各批只有 0.2%–3.7%。
- 眼位、安全两维**实际影响决策**：落子序列逐种子比对（`seqdiff.py`，比玩家、Pass、落点与类型、提子），Eye 0 vs Eye 50 / 100 / 200 / 400 **均为 0 / 200 局相同**，首次分叉中位在第 3–5 个小回合；Safety 10 vs 35 为 0 / 200，Safety 20 vs 35 为 9 / 200。选定组合里占比最大的是 Eye（中位 47.8%）与 Safety（32.2%）。Eye 为 0 时 Safety 中位占比 80.1%，真正可能主导的是 Safety 而不是 PowerGain。
- 对照：Threat 0 / 10 与 25 分别有 159 / 162 局逐步相同，首次分叉最早在第 14 个小回合，即 Threat 在 25 以下只在发生接触之后才起作用。
- **结论：PowerGain 未淹没其他维度，不需要对数刻度**（R22 未触发，不向用户申请启用）。
